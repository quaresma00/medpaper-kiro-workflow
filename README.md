# MedPaper Pipeline (Kiro)

一套面向医学与临床研究的 Kiro 工作流：从研究想法和真实数据出发，完成可发表性判断、研究方案、数据分析、医学表图、论文写作、独立审阅、作者确认和期刊投稿文件制作。目标是形成医学读者能看懂、数据与文献可核实、符合当前期刊要求的论文与投稿包。

适合临床队列、回顾性研究、数据库挖掘（如 FAERS、JADER 等自发报告库）、真实世界研究、预测模型等医学项目，也可以从已有数据、已有分析或半成品稿件继续。数据处理用 Python，图形默认用 R；每节写完立即由医学编辑润色；独立审阅和作者确认放在关键关口；最终投稿由用户自己完成。

当前版本：`1.26.1`　｜　流程：25 个阶段　｜　运行环境：Windows + Kiro IDE + R 4.3+

## 25 步流程一览：每一步做什么、注意什么

下表按**实际执行顺序**排列。编号保留历史编号，所以中间是 **S08 Methods → S10 表格 → S11 图片 → S09 Results → S12 对账**。每个阶段是一道质量关口：门禁通过就接着往下做，不需要每一步都等你说“继续”。

每一步的具体命令、产物和门禁写在阶段卡片 `pipeline/stages/` 和长版说明 `reference/stage_details/` 里（英文，供执行的 AI 读取）。

| 实际顺序 | 每一步做什么 | 关键注意点 |
|---|---|---|
| 1．S01 研究问题 | 把想法整理成结构化研究问题：设计、人群、暴露、对照、结局、数据来源 | 不猜测事实；只问会改变设计的问题，以及目标期刊是否已定；不收集作者信息 |
| 2．S02 可行性 | 用真实 PubMed 检索了解已有研究、研究空白和饱和度 | 结论为 GO / PIVOT / STOP；可发表性检查点为 NO-GO 时立即告诉你 |
| 3．S03 研究方案 | 确定纳排、变量、统计计划，以及完整数据范围和取全的证明方法 | 不强制注册（系统综述按资格注册）；报告清单只在期刊要求时才做 |
| 4．S04 完整数据 | 全量获取数据，建立变量字典、来源记录和数据概要 | 数据原地只读登记，不复制；不抽样、不截断、不漏页；按设计下限核对样本量 |
| 5．S05 数据分析 | 参照同类研究的方法完成主要、次要分析和必要的有效性检查 | 数字只来自代码写出的结果文件；此时不画正式图；追加分析先说明可能改变哪个结论 |
| 6．S06 方案定稿 | 按结果定稿方案，在沙箱里重跑一次证明结果可复现，第二次判断可发表性 | 复现只在这里完整跑一次，之后按哈希复用；确定暂定期刊的版面参数 |
| 7．S07 表图规划 | 参照最新 5–10 篇同类原创论文的实际表图，规划正文和补充表图，先写好图注 | 正文表图数不少于同类论文中位数，少做要写理由；建立展示词典（内部名称 → 临床名称） |
| 8．S08 Methods | 临床写作代理撰写方法，医学编辑代理立即润色 | 正文只写理解和复现所需内容，实现细节放补充方法 |
| 9．S10 表格 | 由代码从结果文件生成医学三线表（xlsx） | 不手抄数字；行列标签用临床名称；看表留到 S23 统一进行 |
| 10．S11 图片 | 默认用 R 从已确认的结果出图，并做确定性质控 | 不为画图重新统计；目视检查推迟到 S23 一次完成 |
| 11．S09 Results | 写作前先由独立代理做科学审阅；再依据定稿的表图写结果 | 你回复“继续写作”才开始写；主要结局先写，阴性结果同样写出估计值和 95% CI |
| 12．S12 对账 | 核对正文数字、表图编号、图注与实际产物一致 | 不一致时改来源，不在三处分别打补丁 |
| 13．S13 文献库 | 按论证角色建立已核验文献库（带摘要，通常约 50 篇） | 每条经 PubMed EFetch 实时核验，保存原始 XML 和哈希；45–60 篇只是 S17 的体检范围，不为凑数检索 |
| 14．S14 Introduction | 临床问题 → 已知证据 → 具体空白 → 研究目的 | 引用只来自核验过的文献库；写作代理起草，医学编辑润色 |
| 15．S15 全文精读 | 精读约 5 篇承担 Discussion 比较的全文 | 只走合法途径获取，并核对全文确实是那篇文章；拿不到时一次列出请你提供 |
| 16．S16 Discussion | 先写 200 词以内的提纲，再比较既往研究、解释机制、意义和局限 | 不复述结果、不引用补充表；局限段必须写出该研究设计的核心提醒 |
| 17．S17 组装 | 自动选题目，写摘要和关键词，组装全文 | 组装后只做跨章节一致性检查，不整篇再润色一次 |
| 18．S18 独立全文审阅 | 一个只读审稿代理从首次读者、编辑、方法审稿人三个角度审阅全文和全部表图 | 检查选择性报告；“必改”定义固定为会改变数字、结论或读者正确理解的问题 |
| 19．S19 作者科学审核 | 审阅轮次：代理按审阅意见修改，你决定再审一轮或确认 | 确认句为“我确认这一版”；同一条消息里一并收集作者等基本信息；确认后冻结科学母稿 |
| 20．S20 选刊与要求 | 选择现实可投的 SCIE 期刊，导入官方投稿指南，生成逐条要求清单 | 已指定期刊时只做核实；指南网页读不到时用浏览器；换刊一条命令，不留旧刊痕迹 |
| 21．S21 作者与声明 | 写题名页和期刊要求的声明 | 只问还缺的或期刊特有的信息；伦理、知情同意、数据可得性先由流程判断 |
| 22．S22 期刊适配 | 只调整该刊实际要求不同的部分（摘要结构、标题、篇幅、拼写等） | 只改期刊副本，不改冻结母稿；改过的段落再交医学编辑 |
| 23．S23 投稿包 | 生成 Word 文件、补充文件、合规矩阵和清单；一次性目视检查全部表图 | 版面参数来自投稿指南；合规矩阵没有 FAIL 才能进入下一步 |
| 24．S24 独立审计与作者确认 | 第一轮就是完整的独立审计（读者、编辑、期刊合规），修改后再复核，你只确认一次 | 你确认的必须是审计者最后读过的那一版；确认后冻结，并复制到 `submission_packages/期刊_日期/` |
| 25．S25 最终核对 | 核对冻结包没有变化，记录 S24 的审计结果，运行最后的自动检查 | 不再启动审稿代理；记 PASS 要求末轮审计结论为 PASS；通过不代表已经投稿 |

**需要你回答的地方**：S01（会改变设计的问题、目标期刊是否已定）；可发表性检查点为 CONDITIONAL 或 NO-GO 时；S09 写作前科学审阅之后（“继续写作”或再审一轮）；S19 确认（“我确认这一版”，并一起提供作者、单位、通讯作者、基金、利益冲突、AI 使用情况，以及 S24 是否查看投稿系统）；S20 尚未指定期刊时选刊；S21 仍缺的信息；S24 确认投稿包（“我确认这一版”）。已经回答过的问题不会再问。“OK”“可以”“继续”都不代替确认句。

**独立审阅有三处**：S09 写作前的科学审阅、S18 全文审阅、S24 投稿包审计（在你确认之前）。审阅代理只读，只写自己的报告；主代理按报告修改，不能自己审自己。

## 当前版本的使用要点

- **论文就在论文文件夹里做**：用 Kiro 打开论文文件夹作为工作区，在那里运行 `wf init`；不会另建子文件夹，也不会让你再去打开别的目录。数据用 `wf data add <路径>` 原地登记，只读，不复制。引擎目录 `F:\workspace\medpaper_pipeline` 只用于维护，运行论文不会改动它。
- **全程在一个对话里完成，不用 Kiro 工作流**：只调用阶段卡片指定的子代理（审稿、临床写作、医学编辑、全文精读）。建议把 Kiro 的 “Use workflows” 设为 “Only when asked” 或 “Only for large tasks”。
- **写作与润色**：每节由临床写作代理起草，医学编辑代理立即润色（去 AI 腔、去工程化叙述、正文用段落而不是列表），数字和引文不变；组装后只检查跨章节一致性，改动过的段落再交编辑。写作原则：先回答研究问题，主要结局先写；阴性和不利结果、局限、不确定性必须报告（`reference/writing_voice.md`）。
- **表图**：表图数量和类型参照最新 5–10 篇同类论文；R 配方包括生存曲线、竞争风险累积发生率、森林图、ROC、校准曲线、决策曲线和火山图，只读取已完成的分析结果；表图里的文字由展示词典换成临床名称；目视检查在 S23 一次完成，省额度但不省检查。
- **期刊**：S20 导入官方指南（先用 API，读不到时用浏览器，再不行请你另存网页），生成带原文和行号的逐条要求清单；S23 生成合规矩阵；S24 审计逐行判断。被拒后换刊用 `wf journal switch`，旧期刊的文件整体归档，新期刊必须按自己的指南重建。
- **返修**：你的意见进入修订轮次（`tools/rework.py`），先定位来源文件和真实依赖，只重建受影响的部分；默认不回退阶段，S19 之后要回到 S19 必须由你回复“我确认回退”。
- **省时间和额度的规则**：已决定的事记在 `.wf/user_decisions.json`，不重复问；复现只在 S06 完整跑一次；长命令用 `--wait` 一次等完；审阅有轮次上限（写作前科学审阅 3 轮、全文 3 轮、投稿包审计 2 轮），到上限后只查回退；`wf report` 列出每个阶段的用时、等待、检查失败、子代理调用和重跑次数。
- **在途论文不受升级影响**：每篇论文锁定它开始时的引擎版本；升级后运行 `wf migrate --yes` 才采用新门禁，论文文件不会被改。

详细变化见[更新记录](docs/CHANGELOG.md)；安装与排错见 [docs/INSTALL-KIRO.md](docs/INSTALL-KIRO.md)。

## 这套工作流解决什么问题

医学论文真正困难的部分不是生成文字，而是让研究问题、数据、统计分析、文献、图表、正文和投稿文件彼此一致，并且符合目标期刊的要求。这个工作流用分阶段推进和自动检查来降低以下常见风险：

- 研究选题已经高度饱和，做完后缺乏发表价值；
- 数据源明明可以全量获取，AI 却为省时间、上下文或算力只取前 N 条、抽样或漏翻页；
- 引用、DOI、PMID、期刊名或年份由 AI 凭记忆生成；
- 正文中的数字没有分析结果作为来源，或表图与正文对不上；
- 正文、表格和图里出现代码变量名、数据处理流水账等工程化语言，医生看不懂；
- 只突出阳性结果，阴性的主要结局、局限和不确定性被淡化；
- 图注重复 Results，表格和图片不像医学期刊文章；
- Word 文件字体、字号、行距、标题层级或版面不符合期刊要求；
- 投稿包缺文件，标题、作者、图表编号、补充材料和声明跨文件不一致，换刊后残留旧期刊内容；
- AI 编造伦理、基金、利益冲突或作者信息。

工作流的目标是：在保证研究有效性和材料一致性的前提下，优先寻找真实、当前、合规且接受概率较高的 SCIE 期刊。Q3、Q4 和低影响因子期刊完全可以作为合理目标；不会为了影响因子牺牲匹配度和现实接受概率。

## 适合与不适合的情况

适合用于临床队列、回顾性研究、真实世界研究、数据库研究、药物警戒不成比例分析、生存分析、预测模型、组学研究及其他可形成医学论文的项目，也可从已有数据、已有分析或半成品论文继续推进。

它不能替代研究者的伦理责任、临床判断和最终署名确认，也不能把数据不支持的结论“包装”成可发表结果。若关键设计、数据质量或统计有效性存在硬伤，流程会给出 `PIVOT`（调整）、`STOP`（停止）或 `NO-GO`，并及时告诉你，而不是继续生成投稿文件。

## 核心处理逻辑

整个流程遵循一条依赖链：

```text
研究问题 → 发表可行性 → 方案 → 完整数据 → 分析结果（S06 复现）
        → 表图规划与 Methods → 实际表格 → 实际图片 → 写作前科学审阅 → Results → 对账
        → 参考文献 → Introduction → 全文精读 → Discussion → 完整论文
        → 独立全文审阅 → 作者审核 → 科学母稿冻结 → 选刊 → 期刊副本 → 投稿包
        → 独立投稿包审计 → 作者确认并冻结 → 最终核对
```

每个阶段都声明自己的输入、输出和通过条件。只有当前阶段的必需文件存在并通过检查，流程才会进入下一阶段。这样可以避免论文先写完、最后才发现数据、文献或图表撑不起正文。

你提出的修改也不会脱离流程。流程先判断修改由哪个阶段负责（例如 Methods 属于 S08，Results 文字属于 S09，统计结果属于 S05，Discussion 属于 S16），再把修改落到分节 Markdown、分析结果、表格或图片等来源文件，重新组装依赖项；不会孤立地改 `full_manuscript.md`。

反复改稿有两个固定入口：S19 审核科学内容和完整论文；S24 审核期刊专属的 Word、投稿文件和跨文件一致性。每批意见保存为一个修订轮次（原话、拆分后的修改项、受影响的来源、验收标准），新意见可以并入尚未结束的轮次；全部修改项完成、相关检查重新通过后才能关闭。轮次数量没有上限。

S19 确认后，`07_manuscript/` 中与期刊无关的科学内容被冻结；S20 以后只改 `08_submission/manuscript/` 里的期刊副本。期刊要求的摘要结构、篇幅、标题页、声明和上传格式都只改这个副本。换刊时从同一份冻结母稿重新生成新期刊的副本，已经确认的科学稿不会被来回覆盖。

这种设计不会用“少读、少改、少检查”换取 token。上下文压缩后流程从磁盘上的状态恢复（`wf status`、`wf handoff`），只读取受影响的来源文件，只重建真正依赖它们的产物，复用未变化且哈希一致的证据。受影响的分析、数值溯源、引用、图表、Word 渲染、人工确认和独立审阅仍照常执行。token、上下文、时间或计算成本都不能成为遗漏修改、缩小研究范围或跳过检查的理由。

贯穿全流程的规则：

1. 数据获取默认覆盖 S03 定义的完整研究数据范围。每个来源都要保存源端总数、实际接收数、末页或游标证据及原始文件哈希；不能为省时间、token、下载量或算力自行抽样、只取前 N 条、限制页数或缩短日期范围。
2. 文献检索工具可以发现候选论文，但正式引用必须重新获取并核验元数据。
3. 正文中的统计数字必须先存在于代码写出的机器可读结果中，不能在写作时心算或补造。
4. 润色只改表达，不能改变数字、引文、表图引用或结论强度；阴性结果、区间和局限不能被删弱。
5. 患者级数据、个人信息、凭据和密钥未经明确授权不得上传到外部服务。
6. 作者、单位、基金、伦理审批、利益冲突等由你提供；AI 使用声明只根据你的实际回答生成。
7. 独立审阅代理只读，只写自己的报告；同一个代理不能既写又审。

## 母版、单篇定制与期刊稿分离

`pipeline/`、`tools/`、`reference/` 和 `.kiro/` 是所有论文共用的母版。运行论文时不会修改这些目录，否则某篇研究的特殊需求会改变以后所有项目；引擎被改动时论文命令会拒绝运行。每篇论文只在自己的文件夹里写文件。简单的数值配置写入该论文的 `.wf/config.toml`：

```powershell
python tools/wf.py config set intro_words_max 600
```

研究设计确实需要不同的流程形状时，使用论文自己的覆盖文件，而不是改母版：

```powershell
python tools/wf.py override init
# 编辑 <论文目录>/.wf/overrides.toml
python tools/wf.py override validate
python tools/wf.py override show
```

覆盖文件可以增加输出和门禁，也可以在写明理由后放宽非完整性门禁，或跳过真正不适用的普通阶段。数据完整性、文献和数字溯源、全文身份、目视检查欠账、科学稿冻结等门禁，以及 S18、S19、S24、S25 的审阅和核对阶段不能关闭。`wf status` 每次都会显示本篇的全部覆盖；阶段完成时会保存覆盖条目的指纹，事后不能悄悄修改。覆盖仍然表达不了时，才在论文内建一份引擎分叉（`wf engine-fork create`），差异留给维护者，全局引擎不动。论文自己的 Python/R 脚本统一用 `wf run-script <相对路径.py|.R>` 运行。

科学稿与期刊稿分开。S19 确认后冻结 `07_manuscript/`；S20 选刊后在 `08_submission/manuscript/` 打开该期刊的副本。被拒后改投另一期刊用一条命令：

```powershell
python tools/wf.py journal switch --to "<新期刊>" --confirm-old "<旧期刊>" --why "<原因>" --outcome rejected
```

它把旧期刊的投稿包、指南快照、审计、投稿包审阅轮次和辅助文件整体归档（保留，不参与任何门禁），回到 S20，再从同一冻结稿生成新期刊副本；新期刊的规则只来自它自己重新导入的指南。科学内容已定稿、只需重新排版时加 `--repackage`。

## 25 个阶段分别做什么

下面按实际执行顺序说明。

### 第一部分：确定研究是否值得做

#### S01｜整理研究想法

把自然语言想法整理成结构化研究问题（`01_protocol/idea.json`）：研究设计、人群、暴露或干预、对照、结局、预期创新点、候选数据源和待确认问题。只问会改变设计的问题，以及目标期刊是否已经确定（已定则 S20 只做核实）；不询问作者、单位等投稿信息。英式拼写只在你需要时才设置，默认美式。

输出：结构化研究想法和贯穿项目的研究笔记。

#### S02｜第一次发表可行性判断

用至少 4 条检索策略在 PubMed 中真实检索，了解已有研究、研究空白和饱和度。`GO` 表示继续，`PIVOT` 表示调整问题或设计，`STOP` 表示当前条件下不宜继续。同时记录第一个可发表性检查点（GO / CONDITIONAL / NO-GO 及可争取的文章类型）；CONDITIONAL 或 NO-GO 时立即告诉你，只问一个问题并附建议。

输出：可行性报告、检索记录和第一次决策。

#### S03｜形成初版研究方案

在看数据之前确定研究目的、设计、人群和纳排标准、变量、主要统计计划和伦理要求，同时定义要获取的完整数据范围、来源、精确查询条件，以及如何证明源端总数与实际接收数一致。不强制公开注册（合格的系统综述按要求在数据提取前注册 PROSPERO），报告清单不预先填写，只在目标期刊要求时补充。

输出：初版方案和数据获取计划。

### 第二部分：让数据和方法形成可靠的结论

#### S04｜获取并登记数据

数据在原位置只读登记（`wf data add`），不复制到论文文件夹。建立变量字典和来源记录，用代码生成数据集概要和缺失情况。`acquisition_manifest.json` 逐个来源核对：源端总数证据、请求数、接收数、是否到达最后一页、原始文件与获取代码的哈希，以及接收记录到分析数据的排除与合并关系。获取代码里的 `LIMIT`、`TOP`、`head()`、`sample()`、前 N 条切片和固定页数会被拦截，且不能用 `--force` 绕过。随后按 `reference/publishability.toml` 的设计下限核对实际样本量，记录第二个可发表性检查点。

输出：原始和衍生数据记录、获取代码、全量获取清单、变量字典、来源记录和数据概要。

#### S05｜方法调研与分析

参照同类研究的方法完成主要、次要分析和必要的有效性检查，所有数字写入 `03_analysis/results/*.json`（Python 或 R 的结果写出器会同时记录运行环境）。派生变量要声明单位和合理范围；多重插补默认按 Rubin 规则合并。此时不画正式图。追加分析前先说明它可能改变哪个结论、大致成本多少，收益低的建议跳过。

输出：分析代码、机器可读结果、分析日志和方法调研。

#### S06｜方案定稿并再次判断可发表性

根据真实数据和分析结果定稿方案，在论文内的沙箱里重新执行一次全部分析，证明结果完全一致；之后的阶段按哈希复用这份证明，只有分析代码、数据或结果变化时才重跑受影响的脚本。记录第三个可发表性检查点，并确定暂定目标期刊或期刊类型，供 S07 设定表图的版面参数。

输出：最终方案、复现报告和第二次 go/no-go 决策。

### 第三部分：先规划证据，再写方法

#### S07｜规划表格、图片和图注

用 `benchmark.py search` 检索最新的 5–10 篇同类英文原创研究（默认近 3 年），读取它们实际的表图数量和类型；正文表图数不少于中位数，多数同类论文都有的表图类型要么做，要么写一句理由。随后写出全部表题和图注（图注只解释设计、分组、符号和统计标记，不复述结果），建立展示词典，把分析中的内部名称映射为临床名称、缩写和一句话定义。

输出：表图计划、同类论文基准、表题和图注、展示词典和暂定期刊参数。

#### S08｜撰写 Methods

临床写作代理根据只含临床语言的写作材料起草（看不到代码、JSON 键名和日志），医学编辑代理立即润色，数字和引文保持不变。正文只保留理解和复现所必需的内容；敏感性分析的实现细节、算法参数等放进补充方法。

输出：Methods；必要时另有补充方法。

### 第四部分：生成读者真正看到的表和图，再写结果

#### S10｜制作医学期刊表格

由代码从结果文件生成三线表（xlsx），主表和补充表分开；行列标签由展示词典换成临床名称，分母、单位、脚注和缩写定义写清楚。表格文字中的代码样名称、软件输出列、科学计数法等会被检查出来。

输出：表格、生成脚本和表格清单。

#### S11｜制作医学期刊图片

默认用 R（`save_medpaper()`）从已确认的结果出图，不为画图重新统计；每张图带渲染回执，脚本或结果变了就必须重新出图。确定性质控检查文字裁切、边距、面板重叠、字号、线宽和分辨率；目视检查推迟到 S23 在最终版上一次完成。

输出：图片、生成代码、质控报告和图注。

#### S09｜写作前科学审阅，然后撰写 Results

先把全部表图放在一张总览图里看一遍，修正看到的问题；表图中仍像分析报告的文字交给临床写作代理改成医学表述。然后由独立审稿代理做写作前科学审阅：研究设计是否站得住、同类论文常有而本文缺少的分析、表图是否充分、结论是否会说过头、能否支撑目标层级的原创论著。审阅后修改分析、表图或方法，给你一份中文小结，只问一个问题：再审一轮，还是“继续写作”。

之后由临床写作代理按定稿表图写结果，医学编辑润色。主要结局写在最前面，无论阳性还是阴性；预设的每个结局都要报告估计值和 CI；事后分析标为探索性。

输出：写作前审阅记录和 Results。

#### S12｜正文、数字、表格和图片对账

确认每个被引用的表图都存在、每个计划的表图都被引用、引用某张表的句子里的数字确实出现在那张表中；再逐个打开表图，核对图注描述的就是图里画的内容。发现不一致改来源。

输出：对账记录。

### 第五部分：建立可信文献基础并完成正文

#### S13｜建立已验证参考文献库

按论证角色（问题与负担、已知证据、研究空白、方法、比较对象、机制等）建立带摘要的文献库，通常约 50 篇；45–60 篇是 S17 组装时的体检范围，不设检索篇数目标，也不为凑数加入无关文献。每条正式文献由 `tools/pubmed/verify.py` 发起新的 PubMed EFetch，把原始 XML、XML 的 SHA-256、解析后的记录指纹和当时 `library.json` 的哈希绑定在一起；门禁会重新解析 XML 并逐项复算 PMID、DOI、题名、作者、期刊、年份和摘要，S13 和 S25 另外实时访问 PubMed 核对。`verified: true` 只是状态字段，单独存在没有证明力。

引用真实性门禁不可豁免，`wf advance --force` 也不能通过。临时脚本、手写 JSON、伪造 DOI，或为了消除警告直接改 `library.json`、`verified.json`、`refs.bib`、`refs.ris`，都会因证据、哈希或实时结果不匹配而失败。唯一正确的处理是换成真实论文，或删除没有来源的引用。

输出：已验证文献库、BibTeX 和 RIS 文件。

#### S14｜撰写 Introduction

四步：临床问题及其重要性 → 已经确立的证据 → 尚未解决、本研究能回答的具体空白 → 一句话研究目的（与最终方案一致）。引用只来自已验证文献库；写作代理起草，医学编辑润色。

输出：Introduction。

#### S15｜精读支撑 Discussion 的核心论文

选取约 5 篇最关键的论文读全文并写结构化笔记。全文只走合法途径：本地缓存 → PMC / Europe PMC → Unpaywall → OpenAlex（含机构库作者稿）→ Semantic Scholar → CORE（需要你自己的 key）→ 预印本 → 你在浏览器中用自己的机构账号登录 → 仍缺的论文一次列给你（题目、DOI、放置文件夹、向作者索取的邮件草稿）。每篇全文都要核对确实是那篇文章；只有摘要时不假装读过全文。

输出：精读索引和笔记。

#### S16｜撰写 Discussion

写作材料只给关键发现的文字描述、主要估计值一次、精读对比要点和已知局限，不给结果表和表图编号。先写 200 词以内的提纲，再写成段落：主要发现、与既往研究比较及差异原因、可能机制、临床意义、局限（具体、写出偏倚方向，并包含该研究设计的核心提醒，例如不成比例信号不等于发生率或风险）、结论。不复述结果，不引用补充表。

输出：Discussion。

### 第六部分：组装全文、独立审阅和作者确认

#### S17｜自动选题目并组装完整论文

根据研究问题和实际结果自动选择最准确的题目，写摘要和关键词，按医学论文顺序组装 `full_manuscript.md`。各节写完时已经逐节润色，组装后不再整篇重做，只运行跨章节一致性检查（术语、缩写只定义一次、引言与讨论的重复句、摘要数字能否在结果或表中找到）；摘要结果先写主要结局，每个效应值都带 CI。

输出：题目、摘要、关键词和完整论文。

#### S18｜独立全文审阅

一个只读审稿代理审阅完整论文、补充方法、全部表格和全部渲染后的图片，从三个角度判断：没看过这个项目的首次临床读者能否看懂、编辑能否接受（工程化语言、表图能否独立阅读）、方法与期刊审稿人是否认可（发表条件、数字、结论强度、选择性报告）。结论为 `READY`、`REVISE` 或 `NOT_READY`，报告原样保存，不转述。

输出：独立审阅报告。

#### S19｜作者科学审核与冻结

这是主要的反复改稿节点，以审阅轮次进行：第一轮就是 S18 的审阅；代理按自己的判断修改能提升质量的地方，涉及数字、分组、结论强度的问题默认修改，只有建议保留时才交你决定。每轮结束给你一条消息：发现了什么、改了哪些文件、哪些没改及原因，并问一个问题：再审一轮，还是确认。同一条消息里会列出还缺的基本信息（作者姓名与顺序、单位、通讯作者及邮箱、基金、利益冲突、AI 使用、S24 是否查看投稿系统），现在答或之后答都可以，只记录一次。

你回复“我确认这一版”后，流程冻结科学母稿；之后的修改只在期刊副本中进行，真正的科学变化必须经你回复“我确认回退”才能回到 S19。

输出：审阅记录、你的确认和科学冻结。

### 第七部分：匹配期刊并制作投稿文件

#### S20｜选择现实可投的 SCIE 期刊

你已指定期刊时只核实它当前被 SCIE 收录、有 JCR 分区且无诚信预警，不再列候选。否则检索近期发表过相近设计和主题的期刊，给出 5–8 个候选和退稿后的备选顺序，按接受概率和匹配度排序，由你选择。官方投稿指南用 `wf journal lookup` 获取，读不到时用浏览器；生成带原文和行号的逐条要求清单，并列出与上一期刊（或默认设置）的差异。随后打开该期刊的副本。

输出：期刊核实或候选、目标期刊信息、指南快照、要求清单和期刊副本。

#### S21｜作者与声明

使用 S19 记录的作者信息，只问仍缺的或该期刊特有的内容（ORCID、CRediT 角色、致谢等）。伦理、知情同意和数据可得性由流程根据研究设计和数据来源判断，并查阅公开来源（数据集许可、平台页面）后起草，只有判断不了的那一处才问你。不编造审批号、豁免或许可。非盲审期刊默认把题名页放在正文首页；盲审期刊只用单独的题名页。

输出：作者信息、题名页和期刊要求的声明（只写在期刊副本中）。

#### S22｜期刊适配

只在 `08_submission/manuscript/` 中调整该刊实际不同的摘要结构、小标题、拼写、篇幅和声明，复用已经润色过的正文；改过的段落再交医学编辑。数字、引文、表图引用和科学含义受保护；按页数估算出来的字数上限只作提示，不作为大幅删减的理由。

输出：适配后的期刊副本和变更记录。

#### S23｜生成并检查投稿包

只生成实际需要上传的文件：正文、需要时的题名页和 cover letter、补充方法等都生成 Word。版面由指南决定；指南没有规定时，正文不嵌图、图注放在末尾、图片单独上传，主表放在参考文献之后、每表一页，补充文件命名为 `Supplemental_File_1_Supplementary_Methods.docx` 这类可读名称。Word 默认 Times New Roman、12 pt、双倍行距、黑色文字，不留黑色小方块（keepNext 等标记）、超链接和手动换行。

合规矩阵逐条记录每项期刊要求的检查结果，没有 FAIL 才能进入下一步。S10、S11 推迟的目视检查在这里用一张总览图在最终版上一次完成，未看过的表图不能放行。

输出：投稿目录、Word 文件、表图、清单、合规矩阵和质量检查记录。

#### S24｜独立审计与作者确认

先处理投稿系统（你在 S19 已答复是否查看；同意时你在浏览器里登录，代理只读，不填写、不提交），把系统与指南的差异落实到文件。然后第一轮就是完整的独立审计：一个只读审稿代理以首次读者、编辑和期刊合规三个角度阅读投稿包，逐行判断合规矩阵，找出要求清单遗漏的义务。代理按报告修改并重建；凡改动过上传文件的轮次立即复核（只看上轮问题是否解决和新的阻断问题），中间不打扰你。

最后给你一条消息：发现了什么、改了什么、审计结论，以及确认请求。只有审计者最后读过的就是你要确认的那一版，确认才会被记录。你回复“我确认这一版”后，投稿包被冻结，并以只读方式复制到 `submission_packages/<期刊缩写>_<日期>/`，从这里上传。

输出：审计与修改记录、你的确认和冻结版本。

#### S25｜最终核对

不再启动审稿代理。核对冻结后的投稿包没有任何变化，把 S24 的审计报告原样记为终审文件（`package_review.py record-audit`），再运行最后的自动检查：分析复现证明、文献实时核验、投稿包完整性、Word 预检、合规矩阵和各项冻结。末轮审计结论为 PASS 才能记录通过；结论为 REVISE 时有两条路：回 S24 复核一轮后重新确认，或由你在终稿副本中亲自修改（`final_copy.py` 检查数字、引文和表图引用不变）。

在 1.26.0 之前冻结的投稿包仍按原方式在 S25 做独立审计。

输出：终审文件和最终结论。

## 在 Kiro 中如何启动

### 一次性安装

```powershell
Set-Location F:\workspace\medpaper_pipeline
python bootstrap.py
```

`bootstrap.py` 会建立 `.venv`、安装固定版本的依赖、接好 Kiro 适配层（steering、两个 hook 和 skill，同时装到用户级 `~/.kiro/`），然后运行 doctor 和回归测试。装完后重启 Kiro 或重新加载窗口。

设置检索需要的环境变量：

```powershell
[Environment]::SetEnvironmentVariable("NCBI_API_KEY", "<你的 key>", "User")
[Environment]::SetEnvironmentVariable("NCBI_API_EMAIL", "you@example.org", "User")
```

`NCBI_API_KEY` 把 PubMed 的请求速率从每秒 3 次提高到 10 次；`NCBI_API_EMAIL` 是 Unpaywall 获取全文所需。可选：在 Kiro 中配置浏览器 MCP（playwright），用于读取需要 JavaScript 的投稿指南页面和投稿系统。

### 日常使用

1. 新建一个论文文件夹，用 Kiro 把它作为工作区打开。
2. 在这个工作区的终端里：

```powershell
python "F:/workspace/medpaper_pipeline/tools/wf.py" init          # 把当前文件夹建成论文（已有论文则继续）
python "F:/workspace/medpaper_pipeline/tools/wf.py" data add G:/data/x   # 数据原地登记（只读，不复制）
```

3. 把研究想法放进 `00_input/`，在对话中输入 `/` 选择 `medpaper-pipeline`，或直接说：

```text
启动 medpaper 流水线，我的研究思路在 #00_input/idea.md
```

同一个对话里启动一次后，后续直接说“修改 Methods……”“这版 Word 的标题格式不对”即可；磁盘上的阶段状态和修订轮次负责约束后续操作，不必每条消息重复触发。换了新对话，代理会先运行 `wf status` 找回当前阶段。

用户级 skill 记录了引擎的绝对路径，所以在任何论文工作区都能找到 `tools/wf.py`。引擎移动位置后重新运行 `python tools/install_adapters.py --global`。

### hook

| Hook | 触发 | 作用 |
|---|---|---|
| `medpaper-status` | 会话开始 | 自动打印当前阶段、门禁状态和上次交接笔记 |
| `medpaper-skill-guard` | 调用工具前 | 拒绝激活会替代某个阶段的技能（`write-paper`、`orchestrate`、`make-figures` 等），对只是部分重叠的技能要求确认 |
| 论文守卫（`wf init` 写入论文自己的 `.kiro/`） | 写入、删除、改名、浏览或搜索文件夹 | 只能写本篇论文；不能读、写或搜索其他论文，也不能改动引擎；你指定的报告文件夹用 `wf config --user report_dirs add <目录>` 声明 |

steering 规则在上下文压缩时可能被摘要掉，hook 不会。被拦截的技能确实无法激活。技能判定写在 `reference/skill_policy.toml`：

```powershell
python tools/hooks/skill_guard.py --audit                 # 列出全部已装技能及其档位
python tools/hooks/skill_guard.py --explain write-paper   # 查看某个技能的判定和理由
```

### 从任意目录调用

在 PowerShell 配置文件里加一个函数（`notepad $PROFILE`）：

```powershell
function wf { python "F:/workspace/medpaper_pipeline/tools/wf.py" @args }
```

之后直接用 `wf status`、`wf check`、`wf report`。提示中的命令会跟随你的调用方式自动切换长短形式。

## 新项目与已有项目如何处理

- 新研究：在论文文件夹里 `wf init`，把研究想法和材料放进 `00_input/`，从 S01 开始。
- 已有数据：先登记数据来源、变量说明和已有分析，再从仍未满足的最早阶段开始。
- 已有论文：工作流会找出缺少的证据链和检查，不会因为已经有 Word 文件就跳过数字、文献和表图核对。
- 中断后恢复：状态保存在论文文件夹的 `.wf/` 中，重新运行 `wf status` 即可看到当前阶段、缺失文件和下一步。
- 引擎升级后：在途论文保持原来的门禁；需要新规则时运行 `wf migrate --yes`。

常用命令：

```powershell
wf status                      # 当前阶段、门禁、上次交接和本阶段卡片
wf check                       # 只显示失败项和一行汇总（完整列表在 .wf/logs/）
wf advance --note "本阶段完成了什么、做了什么决定、还有什么问题"
wf decisions show              # 已记录的用户决定（问用户之前先看这里）
wf report                      # 运行记录：每个阶段的用时、等待、检查失败、子代理调用、复现和重建
wf rebuild --wait              # 投稿包按依赖一键重建并重新测量
wf journal switch --to "<新期刊>" --confirm-old "<旧期刊>" --why "<原因>"
wf migrate --yes               # 在途论文采用当前引擎的门禁
wf doctor                      # 检查运行环境、R 包、适配层和引擎完整性
```

日常使用时，你通常只需要在 Kiro 对话中描述任务、回答关键问题；这些命令主要用于安装、排错或人工查看流程状态。

## 主要文件放在哪里

阶段卡片里的 `project/` 是逻辑名称，指当前论文文件夹，不是引擎中的目录。

```text

04_tables/         主表和补充表
```

研究数据和生成结果永远不进入引擎仓库；每篇论文单独存放，需要版本管理时在论文文件夹内单独 `git init`。

## 文献、隐私与合规边界

- 学术全文只通过开放获取或你明确授权的机构访问获取，不使用非法下载源。
- 文献发现工具只提供候选，不能单独作为正式参考文献的依据。
- 正式引用必须通过新鲜的 PubMed EFetch 原始 XML、内容哈希、当前文献库哈希，以及 S13 和 S25 的实时复核；`verified` 字段、编译成功或门禁变绿都不是文献真实的证据。
- 未经你明确授权，不把患者级数据、私密文件、浏览器 cookie、API 密钥或个人联系信息发送到外部插件或服务；不保存你的登录信息。
- 作者身份、基金、伦理审批、利益冲突由你提供，工作流不推断；能从公开来源查证的事实（如数据集许可）由流程查证并记录来源网址。
- 本工具辅助研究组织、分析、写作和质量检查，不代替研究者、统计师、伦理委员会、期刊编辑或法律、临床专业意见。
